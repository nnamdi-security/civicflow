# Testing

## Must be unit tested
- Status state machine: every allowed and disallowed transition.
- SLA calculation: boundaries, timezone/UTC, pause/resume, reopen.
- Routing: matching, tiebreaks, fallback.

## Integration tests
Run against a real PostgreSQL + PostGIS instance (docker), not mocks. Cover repositories, spatial queries, and pg-boss job handlers (idempotency).

## Adapters
Tests use the in-memory fakes; no test calls a real vendor.

## E2E
A small Playwright suite for the core journeys (report → track → confirm). Phase 3 covers sign in → report with pin and photo → see it in "My reports" → another resident gets a 404. Phase 4 adds report → routed to an agency → another agency's officer gets a 404 → the assigned officer acknowledges → the resident sees the new status and history (the spec creates and removes its own jurisdiction, agencies and officers). Phase 5 adds: an overdue report is escalated by the real scan (run twice, the second records nothing) and both the resident and staff see the overdue notice until the officer acknowledges it. Phase 6 adds: confirm a phone number with the texted code (including a wrong code and an invalid number), turn SMS on, then see the real dispatcher send the received, routed, acknowledged and resolved emails and the resolved SMS to the dev outbox, never containing the description or location, and nothing more on a second run. Phase 7 adds: the officer resolves, the resident tries to say "not fixed" without a note (refused), then with one (the report reopens and the resolution timer restarts), staff fix it again and the resident confirms; then a signed-out visitor finds the report by its code typed any way and sees only the allow-listed fields (no description, notes, photos, email or coordinates; `noindex`), unknown and malformed codes are 404; and a publicly overdue report appears on the overdue board and its public page. The E2E server runs with `PUBLIC_OVERDUE_BOARD=true`; the default-off behaviour is covered by unit and integration tests. Phase 8 Part A adds two journeys: a platform admin creates an agency, gives it an area and a priority, changes an SLA deadline (with a required reason) and invites an agency admin and an officer; a resident's report is routed to the new agency and the officer acknowledges it; the officer is refused (404) on every admin, staff and performance page; the agency admin sees only their own agency's performance (acknowledged 100%, small sample) and only their own agency's staff; the platform admin sees all agencies; and the audit log lists the changes without the invited people's emails. The second journey deactivates an officer (their open session ends on the next request, no new sign-in link is sent, and the page still says "check your email"), then reactivates them. The spec restores the shared roads SLA policy and removes everything it created. Phase 8 Part B adds `security.spec.ts` (headers present, a new CSP nonce per request that Next.js stamps on its scripts, the browser genuinely blocking loads from an unknown site, and the public pages, report form, map and photo upload all running with zero policy violations) and `accessibility.spec.ts` (axe-core, WCAG 2.0/2.1 A and AA, on every public, resident, staff and admin page in realistic states; the third-party map widget is excluded). Each spec resets the sign-in rate-limit counters when it starts, since every test shares one client address. `privacy-journey.spec.ts` covers the resident's rights: download a copy of their data (a real file download, parsed and checked, containing no secrets), a wrong confirmation word is refused, erasing the account signs them out, sends one confirmation email to the old address, leaves the report publicly trackable without their description, and, once the photo-cleanup job runs, the photo is really gone (the dev photo route turns from 200 to 404); signing in again with the same address starts an empty account. The error boundary pages (`error.tsx`, `global-error.tsx`) are not exercised by an automated test. The triage and reassignment screens are covered by integration tests of the use cases, not by E2E. Run with `pnpm test:e2e` (needs `TEST_DATABASE_URL` and a one-off `pnpm exec playwright install chromium`). It starts `next dev` on port 3201 against the test database, reads sign-in links from the dev outbox, uses the dev media store, and stubs map tiles so it does not touch the network. It runs in CI after the unit and integration tests.

## Tooling
Vitest for unit and integration; Playwright for E2E. Run with `pnpm test`.
